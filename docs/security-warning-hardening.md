## 2026-09-25 合意済みの追加実装

### F-030 利用者による削除と管理側の保持

`chat_sessions.user_deleted`（既存行・新規行はfalse）を追加する。利用者の削除操作はtrueへの更新とし、質問・回答・理由・コメント・評価を物理削除しない。別テーブルへの退避や、今回の変更による期限付き自動削除は行わない。

- 利用者側：履歴一覧・検索・詳細・名称変更・質問追加・評価変更・会話記憶で削除済みを除外。ID指定や作成APIの再送による復活も拒否する。
- 管理者側：adminのチャット履歴・出力・ダッシュボード集計には削除済みも含める。staffの本人向け履歴出力は削除済みを除外する。
- 過去に物理削除されたチャットは、この変更で復元されない。既に生成中だった回答の処理を強制終了する機能ではない。

### F-007/F-009/F-016/F-018/F-031/F-032 承認された制限

設定は既存の `infrastructure/config/development-ci.json` と `customer-validation.json` に追加。変更後のデプロイで反映する。UIへの設定メニュー追加はない。

| JSON設定 | 環境変数（ローカルcomposeでも設定可能） | 初期値 |
|---|---|---|
| chatRequestsPerMinute | CHAT_REQUESTS_PER_MINUTE | 10 |
| chatMaxConcurrentRequests | CHAT_MAX_CONCURRENT_REQUESTS | 1 |
| reportExportMaxRows | REPORT_EXPORT_MAX_ROWS | 10000 |
| excelExpandedMaxMb | EXCEL_EXPANDED_MAX_MB | 100 |

すべて正の整数。0による無効化はしない。

- チャット：認証済みの同じサイト・利用者IDをまとめ、直近60秒の受付数をDBに保存する。複数タブ・複数バックエンド・再ログインでも合算する。同時処理中の要求数はPostgreSQLのロックで制御する。生成失敗も受付回数に含む。同時数・回数で拒否された要求は追加カウントせず、429と再操作の案内を返す。回数超過にはRetry-After秒数も返す。FAQ・生成AI・会話確認を同じ枠で扱う。サーバー再起動後も回数は引き継ぎ、処理終了・異常終了では同時数ロックを解放する。ロック専用DB接続を使用し、通常クエリの接続プールを占有しない。
- 履歴・ログ出力：チャット履歴（質問・回答1組で1件）、アクセスログ、操作ログが対象。検索条件・権限・操作種別をSQLで適用して最大「上限+1件」だけ取得し、上限超過なら422で拒否する。先頭だけのファイルは作らない。FAQ等のマスタ一覧・ユーザリストへの新たな件数上限はこの変更で追加しない。
- Excel：FAQ取込・データソース一覧取込・Webサイト一覧取込・Excel文書追加／変換で、ZIP内全ファイルの展開後サイズ合計を検査。100MBは100×1024×1024 bytes。申告サイズを先に検査し、実展開も小分けで計測してからExcel解析へ進む。超過時は登録前に422と削減・分割の案内を返す。既存のアップロード容量・登録件数の制限も引き続き適用する。バックエンドと変換ワーカーに同じ設定値を渡す。

## 設定と移行上の注意

### ローカルcompose

`.env` に以下を設定する。新規環境ではそれぞれ異なる十分長いランダム値を生成する（例：`python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`）。秘密値はコミットしない。

- `ACCESS_LOG_SIGNING_SECRET`：フロント・バックエンド間のアクセス記録専用鍵。両コンテナに同じ値を設定。ブラウザには渡さない。AWSでは専用Secrets Managerリソースを作成・注入する。
- `LOCAL_DB_PASSWORD`：DB用。既存DBボリュームを使う場合は現在のDBパスワードに合わせる。環境変数変更だけでは既存DBのパスワードは変わらない。
- `ANALYTICS_IDENTITY_SECRET`：既存環境では現在の値を維持する。安易に変更すると履歴の利用者識別が変わる。
- `CPF_DEVELOPMENT_JWT_SECRET`：開発用JWT署名鍵。疑似ログインの共通パスワードとは別物。

アプリをcompose外で起動する場合は `DATABASE_URL`、または `DB_HOST` と `DB_PASSWORD` を明示する。AWSでは従来どおりSecrets ManagerからDB認証情報が供給される。

### CSRFと接続元IP

- `CORS_ALLOWED_ORIGINS`：フロントエンドの正確なoriginをカンマ区切りで設定。`*` は使わない。スクリプトでCookie認証の更新APIを呼ぶ場合も正しい `Origin` ヘッダーを送る。
- `TRUSTED_PROXY_CIDRS`：プロキシとして信頼するIP範囲。未設定ならX-Forwarded-Forを無視する。CDKではVPCのCIDRを設定し、ECSへの入口をALBのSecurity Groupに限定する。新規ALBはappendモード（ポート付与なし）を明示する。既存ALBは実際の設定を確認する。既存ALBや別プロキシ経路がある場合は設定確認が必要。
- アプリ前段で勝手にIPを書き換えないよう、AWSのuvicornは `--no-proxy-headers` を指定。compose外の独自起動でも同様にする。

### サーバー側アクセス記録

Next.js `proxy.ts` が `/chat` と管理画面へのGET要求を分類する。ログイン・API・静的アセットは対象外。ブラウザからのアクセス記録送信は廃止する。

- `ACCESS_LOG_API_URL`：固定のバックエンド記録先。AWSは公開ドメインの `/api/v1/analytics/accesses`、composeは `http://backend:8000/api/v1/analytics/accesses`。
- `ACCESS_LOG_ORIGIN`：バックエンドで許可するフロントのorigin。
- `ACCESS_LOG_SIGNING_SECRET`：サーバー専用。ブラウザ公開用の `NEXT_PUBLIC_` 変数には絶対にしない。
- 署名は認証Cookie・ページパス・本文（転送IPとUAも含む）を結び付ける。利用者IDと時刻はバックエンドで確定し、本文のサイト区分は信用しない。
- 画面要求の記録であり、利用者が画面を読んだことを保証するものではない。ブラウザ内のキャッシュだけで表示が切り替わり、サーバーに要求が来ない場合は新規記録がない。一方、ページの先読み要求もサーバーに届いたGET要求として含む。
- 記録通信に失敗しても画面を止めず、フロントのサーバーログに障害を記録する。
- AWSは `domainName` を必須とする。リクエストのHost値を記録先URLとして使用しない。

### 回答保存API

`/chat/messages` は認証済み利用者が所有する `chat_session_id` と `interaction_id` を必須とする。画面・検証スクリプトも同時更新する。古い画面を開いたままの場合は再読み込みが必要。
回答完了日時はサーバー保存時刻となる。履歴・評価の保存は維持し、利用者による削除の扱いは上記F-030の追加実装に従う。

### リハーサル

新規の `rehearsal-...` 名、HTTPS証明書ARN、対応する一時ドメインが必要。DNSは対象環境へ設定する。既存スタックは再利用しない。ワークフローの入力だけではDNSレコードを作成しない。
